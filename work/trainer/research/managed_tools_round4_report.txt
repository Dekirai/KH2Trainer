1. These caches are serialized object memory
-------------------------------------------
The model, motion and sound source nodes all occupy168 bytes in this build:

  +0x00  eight-byte native vtable pointer
  +0x08  eight-byte linked-list next pointer
  +0x10  sixteen MD5 digest bytes
  +0x20  four-byte little-endian signed original-file length
  +0x24  NUL-terminated narrow path, followed by unspecified object bytes

The remaining object storage from+0x24 to the end is132 bytes. This is NOT proof
of a132-byte declared path array: a128-byte array plus tail alignment padding is
also compatible with this size. Metadata supplies only an alignment member.
The path codepage is not specified in these bodies. Both uncertainties remain
explicit; no legacy-cache importer has been added to the product.

There is no file magic, version, record count or checksum. Writing the complete
node includes vptr/next and any uninitialized padding. Those pointer bytes have
no meaning in a different process. A future importer must discard them rather
than attempt object reconstruction. Paths must remain inert text, never implicit
requests to open the original development network shares.

2. Destruction writes the cache
-------------------------------
The model constructor CIL0x1D20 initializes its native list and immediately
scans //kh2/proj/interdata/*. The motion constructor0x1E30 passes the same
fixed mask to the native motion scanner, which may instead use its cache.

The destructors0x1D60/0x1E70 open these files with wb:
  //caelum/proj/KH2-CharExport/kh2_model_list.bin
  //caelum/proj/KH2-CharExport/kh2_motion_list.bin

They write168 bytes for every source node, ignore fwrite/fclose results, then
delete nodes and reset their lists. If opening succeeds, even an empty list
truncates the old file. There is no separate explicit save confirmation in these
bodies and no transaction or rollback.

Sound destructor0x2180 has the same pattern for:
  //caelum/proj/KH2-Sound/kh2_sound.bin
Only the source list is persisted. Its separate BAR-match result list is freed
without being written to the cache.

3. The sound cache reader advances correctly, but trusts each record
-------------------------------------------------------------------
CIL0x2010 creates source/result lists at this+0x80/+0xA0, opens the sound cache
rb and repeatedly fread(temp,168,1,file). Each complete record becomes a freshly
constructed source node. Digest/length/path are copied; the serialized vptr and
next pointer are not adopted. A new fread occurs for every iteration.

This differs from the earlier confirmed native motion-cache defect at
0x140563ED0, whose loop repeats its first record. That defect is supporting
context, not a new discovery in this tranche.

The sound path nevertheless treats EOF, a partial trailing record and read
failure alike. An opened empty cache suppresses fallback scanning. Only failure
to open chooses //kh2/proj/sound/* and native0x140564EB0. There is no explicit
NUL/length/codepage validation for the serialized path. That path is passed as
the sprintf format in0x1F60 and in the cache reconstruction. A later destructor
can replace a cache that was only partly read with its shorter in-memory list.
These unchecked operations are static findings, not exercised exploit claims.

4. Container ownership and result lifetime
------------------------------------------
List constructors initialize a32-byte vptr/head/tail/count object. Their native
destructors only reset vptr; they do not traverse and delete contained nodes.
The owning searcher destructor performs that traversal explicitly. Compiler
deleting-destructor wrappers at CIL0x31F0/3290/32E0/3330 handle the list object
itself with32-byte array stride;0x3240 handles a16-byte SoundList base joint.
They trust the compiler array cookie at this-8 and deletion flags.

SoundList default constructor0x1F40 initializes the joint and vptr only. Its
payload remains unspecified. Destructor0x2000 only calls the base joint dtor;
deleting wrapper0x1FB0 handles scalar/array allocation release with168-byte stride.

getIndex0x22C0 searches results by ordinal and writes index/tag/path outputs only
when a node is found. There is no success result, no output initialization on a
miss, and returned strings are borrowed from the node. Native0x1405649F0 stores
the immediate BAR index and tag but flattens nested ancestry. A sound match list
therefore cannot uniquely identify all same-tag entries from nested containers.

5. Raw BAR offsets are not decoded pointers
-------------------------------------------
CIL0x2320/2330 call native0x14038CBD0/38CBE0 on entry+8. The native bodies are
simply a uint32 load/store. They do not add a container base or decode a packed
runtime pointer. The existing offline reader correctly treats disk-relative
offsets separately and rejects relocated containers. This unchecked setter is
documented only; it is not exposed by the new tool.

Useful implementation
----------------------
The portable fingerprint index now implemented in new Core files replaces no
legacy file and calls no engine helper. It hashes one explicitly selected loose
file, package-original/remastered payload or nested BAR entry through the
existing bounded AssetArchiveReader. It retains source label, every BAR ordinal,
type/tag, parent metadata digest and package/remaster ordinals. Equal names or
shared byte ranges remain distinguishable.

SHA256 plus byte length is the default content match. Optional MD5 plus length
is labeled a legacy match, never proof of byte equality/provenance. Every match
is retained. The versioned JSON contains descriptive portable locators, not
absolute local paths or executable object pointers. Loading a saved index does
not open its assets or resolve paths. See managed_tools_round4_fingerprint_api.txt.

This is an additional asset-comparison tool, not another extraction backend or
a live trainer command. It does not decode animations/models, restore lost
source filenames, prove ownership of content or reproduce the developer share.
