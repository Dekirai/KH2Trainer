RETRY / GAME-OVER — STATIC FINDINGS

Native checkpoints contain structured SaveData, a ten-byte map target and two
auxiliary blocks. They do not capture the complete actor or script runtime.
The existing trainer retry action uses the native scene teardown/reload route;
an arbitrary checkpoint-capture action would not produce a full combat rewind.

Game over owns a 136-byte context and an asynchronous task. Mickey rescue
passes through partner checks, resource loading, party suspension, menu
callbacks and a separate character creation phase. Directly invoking a factory
outside that lifecycle is not established. The trainer therefore offers the
validated rescue-use counter and diagnostics documented in rescue_control.txt.

The saved rescue-use count is distinct from the recorded MICKEY APPEAR count.
The count-dependent threshold is conditional on the native game-over type,
mission permission and partner checks; it is not a guaranteed rescue setting.

Useful applications: inspect rescue behavior and compare checkpoint-restored
progress during practice. Future work: precise per-mission rescue requirements,
the unresolved menu labels, and safe native actor-loading contexts.

retry_gameover.json contains address-specific findings and explicit limits.
retry_gameover_evidence.json preserves the fresh decompilation and full ASM.
No live game calls, process-memory changes or UI tests were performed.
